# Evaluation

## The question

Cybersum does two things that could each explain a better briefing: it structures
the input with SQL, and it uses a long, specific prompt. Comparing "Cybersum"
against "a model given raw logs" would conflate them and prove nothing about
either.

So three groups, arranged so each arrow moves one variable:

| Group | Input | Prompt |
|---|---|---|
| **A** — baseline | the 50 most recent raw JSONB log rows | short generic summarisation prompt |
| **B** — control | the 50 most recent raw JSONB log rows | the full Cybersum prompt |
| **C** — Cybersum | the aggregated context | the full Cybersum prompt |

A → B holds the data constant and changes the prompt. B → C holds the prompt
constant and changes the data. A → C is the system as a whole.

## Setup

Five synthetic scenario windows escalating from quiet to critical, generated by
[`evaluation/synthetic_data.py`](../evaluation/synthetic_data.py) and modelled on
CICIDS 2018 traffic characteristics:

| Window | Label | DDoS risk | Malicious traffic | Abnormal services |
|---|---|---|---|---|
| 1 | STABLE | 5.0 | 5% | none |
| 2 | STATUS_A | 15.0 | 12% | none |
| 3 | STATUS_B | 35.0 | 28% | none |
| 4 | STATUS_C | 62.0 | 45% | 1 paused |
| 5 | STATUS_C | 80.0 | 61% | 1 paused, 1 down |

5 windows × 3 groups = 15 briefings. Each is scored by GPT-4o on three
dimensions, 1–5, averaged over **three judging runs**. The judge receives the
aggregated context as ground truth and **no group label**, so it cannot know
which arm it is reading. The rubric is a single file
(`prompts/geval_rubric_v3.txt`) used by both scoring paths — an identity
assertion in the test suite keeps it that way, because two copies of a rubric
means two judges and an incomparable table.

## Results — the thesis run

Group means across all five windows:

| Dimension | A (baseline) | B (control) | C (Cybersum) |
|---|---|---|---|
| Factual accuracy | 2.53 | 1.07 | **3.13** |
| Completeness | 3.13 | 2.40 | **4.47** |
| Situational awareness | 3.13 | 2.73 | **4.67** |
| **Overall** | **2.94** | **2.07** | **4.09** |

Effect decomposition:

| Comparison | Isolates | Effect |
|---|---|---|
| A → B | prompt engineering | **−0.87** |
| B → C | SQL aggregation | **+2.02** |
| A → C | combined | **+1.15** |

Per window:

| Window | Scenario | A | B | C | A → C |
|---|---|---|---|---|---|
| 1 | STABLE | 3.45 | 2.78 | 4.67 | +1.22 |
| 2 | STATUS_A | 3.67 | 2.56 | 3.78 | +0.11 |
| 3 | STATUS_B | 3.67 | 2.45 | 3.67 | 0.00 |
| 4 | STATUS_C | 2.00 | 1.33 | 4.22 | **+2.22** |
| 5 | STATUS_C | 1.89 | 1.22 | 4.11 | **+2.22** |

## Reading it

**The structured prompt, on its own, is harmful.** −0.87 is not noise. Group B
scores 1.07 on factual accuracy — near the floor. Asked for a status
classification and a specific set of metrics over fifty random rows that mostly
do not contain them, the model produces confident, specific, wrong text. The same
prompt over aggregated data is the best arm. Prompt engineering is not
independently good; its value is contingent on whether the input can support what
the prompt asks for.

A note on the sample. The thesis describes it as random; the code takes the 50
most recent rows by `event_timestamp`, and this repository preserves that rather
than changing what was measured. Either way the argument is the same — a
fixed-size slice of a table dominated by routine traffic usually misses the rare
critical row — but "most recent" is what the numbers came from.

**The benefit is concentrated in the severe windows.** Windows 2 and 3 show
+0.11 and 0.00 — on a quiet day, a random sample and an aggregate say much the
same thing. Windows 4 and 5 show +2.22 each. That is where a paused service and a
critical DDoS score live, and fifty rows from a table dominated by routine
traffic will usually miss them. The judge on window 4, Group A:

> *"The report incorrectly states that the infrastructure is stable, while the
> ground truth shows the Main Web Portal service is Paused and DDoS status is
> CRITICAL."*

A briefing that reports a crisis as a quiet day is not a slightly worse briefing.

**Cost.** Group A averaged 3,353 prompt tokens, Group C 4,411 — a 31.5% increase
for a 39% score improvement, and structurally flat: the aggregate does not grow
with the log table, whereas a raw sample large enough to be representative would
have to.

**Group C's ceiling.** Factual accuracy stops at 3.13 while completeness reaches
4.47. That gap is one specific, reproducible error, and it has its own writeup:
[findings.md](findings.md).

## The re-run

`evaluation/outputs/runs/2026-08-12/` is the same experiment on the current code,
with the grounding fix in place and data regenerated from a different seed:

| | Thesis run | Re-run |
|---|---|---|
| Group A | 2.94 | 2.67 |
| Group B | 2.07 | 1.80 |
| Group C | 4.09 | **4.91** |
| A → B | −0.87 | **−0.87** |
| B → C | +2.02 | **+3.11** |
| A → C | +1.15 | **+2.25** |

Group C's factual accuracy went 3.13 → 5.00, which accounts for most of the
change. Groups A and B each fell 0.27, so the prompt effect is unchanged at
−0.87 — an effect measured twice, on different data, by different judging
sessions.

`python -m evaluation.cli compare evaluation/outputs/published evaluation/outputs/runs/2026-08-12`
prints them window by window.

## Limitations

- **One judge, unvalidated.** GPT-4o scoring GPT-4o output. No human evaluation
  was run to check the judge tracks human judgement. The thesis planned a blind
  panel of 3–5 evaluators and used G-Eval instead; closing that gap is what would
  make these numbers portable.
- **Five windows.** Enough to separate a 2.02-point effect from noise. Not enough
  for a confidence interval worth quoting, and the per-window spread (0.00 to
  +2.22) is wide.
- **Synthetic data.** Fabricated windows modelled on published traffic
  characteristics, not a real attack corpus with real ambiguity.
- **The side channel was never tested.** The evaluation prompt omits the
  `###DATA_START###` instruction, so these results measure the prose contract
  only. See [prompts.md](prompts.md).
- **The archive does not reproduce.** The thesis numbers came from code that has
  since been refactored, and one field in their recorded ground truth is emitted
  by no surviving code — `evaluation/outputs/published/README.md` documents it.
  They are preserved as reported. The re-run above is what the current code
  produces, and the two are not the same measurement: different data seed,
  different judging session, and a fixed aggregation.
- **Scores are not comparable across runs, only within one.** Groups A and B each
  fell 0.27 between runs with no relevant change to either arm. Read the arrows,
  not the absolute levels.
